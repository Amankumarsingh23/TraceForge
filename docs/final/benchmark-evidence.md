# Defensible performance evidence

The authoritative measured experiment is [Session13](../benchmarks/session-13.md), including committed query/DDL/EXPLAIN/checksum data under `docs/benchmarks/session13/`. Final SQL run `20261114132435` used deterministic seed42,100,000 and300,000 logical spans with100,023/300,096 physical replay/conflict rows and corresponding log fixtures. The host was an i5-12500H/16GiB Windows system; Docker/WSL exposed16 CPUs/about8GiB, ClickHouse26.8.36.3. Queries used two threads,20-second/512MiB budgets. No cold OS/page-cache claim.

The controlled index comparison disables both query-result caching and query-condition caching (`use_query_cache=0`, `use_query_condition_cache=0`) and compares identical trace-ID correlation predicates/results. At300k, baseline read300,096 rows/38 selected marks; trace-ID bloom read8,192 rows/one mark. Reduction=(300096−8192)/300096=97.2702%; scan ratio36.6328. Disk overhead at the controlled snapshot was approximately0.43%. This is reduced scan work, not36× product or production latency speedup.

One warmup/ten sequential repetitions were used; nearest-rank p95 is the maximum at ten samples. At300k the cache-controlled SQL HTTP p50/p95 was11.08/36.33ms baseline versus7.64/31.24ms indexed. HTTP measurements include client/network overhead and differ from ClickHouse QueryFinish durations. Separate Go API tests recorded production-engine/result equality and correlation body checksums; API p95 did not consistently improve. Background merges, part layout, warm caches, sequential order and concurrent local workloads limit latency attribution.

The first warm comparison left query-condition caching on and both sides eventually read8,192 rows. That result cannot establish bloom-index pruning; the later disabled-cache experiment does. Session14 repeated the isolated experiment and retained equal checksums and the same scan pruning; its timing varied under concurrent verification. Session15 preserves those raw results rather than inventing a new benchmark run or capacity number.

The measured ingestion/ACK evidence is a separate local workload: Session13 offered/acknowledged10,000 spans in100 RPCs while30 trace reads ran, with zero rejected/unknown outcomes in that run. See raw benchmark report for latency distributions. It is not sustainable production throughput. Independent real SDK traffic verifies signal/count/canonical invariants rather than SQL insertion throughput.

Rejected alternatives remain documented: service-first layout increased exact-trace rows8,192→23,830 and storage6,812,610→10,480,182 bytes at300k; codec savings were confounded by repetition/part state; conflict-excluding snapshots were not equivalent incremental canonical aggregation. No general preaggregation or sorting-key migration was adopted. Reproduce the isolated experiments with `scripts/session13/benchmark.py`, `index_cache.py` and the tagged Session13 integration tests after privately loading database configuration; never run destructive retention against the primary raw tables.
