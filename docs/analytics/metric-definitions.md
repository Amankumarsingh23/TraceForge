# Trace-derived analytics contract: trace-red/v1

This contract summarizes observed spans. It does not ingest OTLP metrics, estimate unsampled traffic, prove business success, or constitute an SLO.

## Canonical observations and identities

An observation is canonical by `(trace_id, span_id)`. Reuse `traces.Reconstruct`: choose earliest `ingested_at`, then lexicographically smallest **full normalized content**, excluding ingestion time, on a tie. Exact replay cannot increase logical counts; conflicting variants remain diagnosed. Canonical selection is deterministic, not proof that the selected observation describes ground truth.

An eligible service has a nonempty resource `service.name` matching the stored extracted name. The ingestion placeholder `unknown_service`, missing names and disagreement are excluded and diagnosed. Identity is `(service.name, service.namespace, deployment.environment.name, workload class)`. Missing namespace/environment remain empty, not a guessed production value. ID is the first 128 bits of SHA-256 over the JSON array of those four strings; filtering and URLs use this ID, so equal names in different scopes remain separate. These hashes are identifiers, not authentication or tenant boundaries.

Explicit resource `traceforge.workload.kind=synthetic|fixture|live` supplies workload class. Otherwise an explicit span `traceforge.provider.mode=fixture|live` is used, else `unknown`. Unknown never means live. The Go gateway/payment demo now marks its shared trace/log resource synthetic; `TRACEFORGE_SERVICE_NAMESPACE` optionally isolates a run. Earlier unmarked records remain unknown. Class is attached to each observed span, so unmarked enclosing agent spans can remain unknown while explicitly marked model operations are fixture/live. There is no name-based guessing or historical backfill.

## Inbound RED and time attribution

- Count: canonical eligible **SERVER** spans whose start is in UTC `[from,to)`. Distinct inbound operations within one trace count separately. INTERNAL, CLIENT, PRODUCER and CONSUMER do not count toward this denominator.
- Rate: count / actual window seconds. No extrapolation from sampling, export success or wall-clock workload scheduling.
- Errors: the same eligible SERVER spans with explicit OTel status ERROR (code 2). Fraction = errors / count. A child error does not alter its parent's status. UNSET (0), OK (1), ERROR (2), and OTHER are shown independently; UNSET is not proven business success.
- HTTP response status is separate evidence from the stable `http.response.status_code` key, recognized only in the 100–599 range; missing/unrecognized values are grouped as `missing`. No legacy-key inference or HTTP-based replacement of OTel status. Non-HTTP observations legitimately have missing HTTP status.
- Duration: the stored canonical nanoseconds, converted to milliseconds. Negative end-before-start or values beyond signed nanosecond range are excluded from duration samples and diagnosed, while operation/status counts remain observed. Zero recorded durations are retained; clock resolution and instrumentation affect these local measurements.
- Mean: sum of duration samples / sample count. Percentile p uses sorted samples at one-based rank `ceil(p*n)`. p50/p95/p99 use the same nearest-rank convention everywhere. Empty duration samples have null mean and percentiles. Duration samples and request count can differ.
- No observations: count and rate zero, error fraction and duration statistics null. Unknown service ID detail can return an empty service list with the applied ID in `query`; the UI explicitly describes this empty scope, without inventing its identity. CLIENT-only observed services have zero inbound RED and empty inbound duration samples.

Buckets start at the requested `from`, not at an implicitly rounded clock boundary. Supported widths: 60, 300, 900 seconds; window at most one hour gives at most 60 buckets/service. The final partial bucket ends at `to`, with **its actual seconds** as the rate denominator. Empty buckets are retained for every returned observed identity. Whole-window counts, errors and percentiles are computed from combined eligible raw canonical samples, never averages of bucket fractions or percentiles. Error fractions are 0–1, not already multiplied by 100. Browser percentages only format this fraction.

## Confirmed synchronous dependencies

An edge requires one canonical CLIENT and exactly one canonical SERVER child in the same trace, with `server.parent_span_id == client.span_id`, valid identities and different identity IDs. Edge direction is caller → callee. A trace or timing coincidence, service-name match, SpanLink, internal child or missing span never creates an edge.

An edge's owning window is the CLIENT start in `[from,to)`. Matching SERVER may start outside that window and is still paired. Each CLIENT span ID contributes at most once. Distinct retry attempt IDs are distinct outbound observations; only attempts with matching SERVER evidence become confirmed pairs. Multiple SERVER children for one CLIENT are ambiguous and excluded, not expanded into arbitrary calls.

`edge.client.count == edge.server.count` is the confirmed pair count; rate is pairs/window seconds. CLIENT and paired SERVER statuses, errors, HTTP status, duration samples/mean/percentiles are computed independently. They are not inbound service-wide denominators. Subtracting SERVER duration from CLIENT duration is not an exact network-latency measurement, so no such metric is emitted. Same-service pairs are excluded and diagnosed. Distinct namespace/environment/workload identities are distinct services even when names match.

Representative trace IDs come from actual eligible operations/pairs. At most five examples are selected deterministically by error first and duration descending, trace ID on ties; when errors would occupy all five, retain one slow non-error example. These are examples, not an exhaustive drilldown. Trace links open the full canonical waterfall; log links open its exact-ID correlated-log panel (the existing panel covers the last 24 hours and labels that limit).

## Bounded bulk reads and failure semantics

1. Discover up to 128 distinct trace IDs with a raw SERVER or CLIENT start in the window. Read 129 as a sentinel; exceeding this fails before hydration. Discovery deliberately does not prefilter service/environment/workload. Raw conflicting variants can create conservative false-positive candidates; canonical filtering still decides final eligibility.
2. One parameterized bulk `trace_id IN (?)` read hydrates **all span kinds and start times** for those IDs. No per-trace SQL and no time filter on hydration. Maximum 20,000 physical rows plus a sentinel; conservative decoded byte accounting ≤16 MiB. This bounded historical hydration preserves cross-window parents/children.
3. Reconstruct each trace with the existing 2,000 physical-row cap and full canonical rules. Bound combined serialized records at 16 MiB. Filter canonical observations, aggregate, pair and render. At most 64 service identities, 128 edges and 4,096 service bucket points; cap allocations as new identities/edges are admitted. These structural limits bound Go state, not a measured or hard process-heap guarantee.
4. Reuse ClickHouse scan guards per SELECT: 1,000,000 rows read, 128 MiB uncompressed read, 256 MiB query memory, 32 MiB result bytes, 2-second execution with throw modes. Both reads share a 3-second storage context inside a 4-second API context. Two analytics requests may run concurrently; excess returns 429. No materialized aggregate, database schema or index change is included.

ClickHouse can check limits after processing a part, so scan/memory settings are protective thresholds, not byte-perfect process isolation. See [official query-complexity limits](https://clickhouse.com/docs/concepts/features/configuration/settings/query-complexity). Parameter values are bound, never SQL fragments. Request cancellation propagates to driver/reconstruction. Known row/byte/memory overflow exceptions become budget errors; execution timeout becomes timeout. Safe HTTP errors do not echo SQL, credentials or driver messages.

Budget failures return **413 / analytics_budget_exceeded**, never silent top-N, partial buckets, approximate percentiles or incomplete success. Invalid filters return 400; timeout 504; cancellation 408; invalid stored data 500; backend unavailability 503. Response JSON is capped at 16 MiB and no-store. Discovery filters apply late, so a narrow identity filter does not rescue an over-budget time window. Narrow the window; do not pretend a larger graph was fully scanned.

Two reads are **not a snapshot**. Late exports, concurrent writes/deletions, sampling, missing instrumentation and Collector failure can alter repeat queries. `selection_complete=true` means the bounded selected hydration was processed without truncation; `completeness` remains unknown for actual traffic and topology. `non_snapshot=true`, applied bounds, units, attribution, budgets and diagnostics are returned. No extrapolated coverage percentage is invented.

Diagnostics cover all hydrated candidate traces before identity filters. Physical/canonical/duplicate/conflicting observations, missing names, general missing parents/cycles/timing warnings are exposed. Window diagnostics separately count unmatched CLIENTs, ambiguous CLIENTs, same-service pairs, SERVER missing parents/wrong parent kinds and invalid duration contributions. These are evidence problems, not proof a remote service did not receive a request. Invalid durations can appear in both inbound and paired contributions. Candidate count is the number of hydrated trace groups.

## HTTP/UI contract

GET `/api/v1/services`, `/api/v1/services/{id}/metrics`, `/api/v1/services/{id}/dependencies`, `/api/v1/service-graph` all return the same versioned envelope, with relevant services and directed edges. Identity detail retains incident-edge endpoints as context; their inbound statistics still mean their own eligible requests. The detail UI selects its requested identity rather than relabeling a neighbor. Detail unknown ID is a valid empty observed scope. The two detail endpoints are aliases over one shared canonical computation, not independent definitions.

Filters: `from`, `to` (UTC RFC3339 with Z, signed nanosecond range); `bucket_seconds`; exact `namespace`, `environment`, `workload`; and overview/graph `service_id`. No unknown/repeated/empty parameters. Defaults are last 15 minutes / 60-second buckets. The overview offers local display sorting by name, descending request rate, ERROR fraction or p95 (missing values last), and explicitly shows duration sample counts. This sorts the complete bounded response without truncation or changing the canonical scope. API fixed deterministic sorting is service name then identity ID; edges caller ID then callee ID. Hard all-or-error result limits replace pagination/top-N in v1; `limit` and arbitrary sort expressions are rejected. Identity filters select incident graph edges while retaining contextual endpoints; environment/namespace/workload must match both endpoints. No fuzzy service matching.

Next.js uses fixed same-origin `/api/services...` and `/api/service-graph` GET proxies with the existing bounded response reader, approved paths, no redirects, server-only configured backend origin, abort and no-store behavior. No client-selected upstream or browser database credentials. `/services`, `/services/{id}`, `/service-graph` offer manual refresh, preserved UTC bounds, identity filters, RED tables, bucket bars with accessible values and deterministic SVG graph plus keyboard-focusable nodes/edges and ordinary links. Empty, loading, invalid, oversized and unavailable states remain visible without fabricated data.

The local Compose ports remain loopback-only. Namespace/environment filters are **not tenant authorization**. Authentication, tenant-enforced query predicates, production TLS and stronger adversarial hardening remain future security work; this interface is restricted local development.

## Compatibility checked

No new dependency or schema migration. Existing Go OTel 1.47.0 / otelhttp 0.72.0 uses `semconv/v1.43.0`; stable HTTP key/status behavior was checked against installed instrumentation and [pinned upstream conventions](https://raw.githubusercontent.com/open-telemetry/semantic-conventions/v1.43.0/docs/http/http-spans.md). SERVER 4xx can remain UNSET while CLIENT 4xx can be ERROR; HTTP and OTel evidence must therefore stay separate. Tests include explicit 404/UNSET and recovered child-error cases. Existing ClickHouse Go 2.51.0 native bulk array binding was verified against the actual Docker backend and local HTTP driver integration.
