# Dataset and review rubric

`examples/agent-demo/evaluation/data/support-eval-v1.json` contains 35 synthetic document-RAG cases: 24 single-topic/paraphrase questions, five two-document questions, one three-document truncation question, and five missing-knowledge/ambiguous/irrelevant questions requiring abstention. Thirty have nonempty relevance labels; five have none. Twelve independent atomic fact entries map exact approved alternatives to D01–D12 evidence quotes from the actual `support-kb-v1` corpus. This uses its real 30-day refund window, 7-day damage-report window and five-synthetic-business-day refund review; teaching examples mentioning photographs or original payment method are not labels for this corpus.

Each case has stable ID, question, relevant IDs, expected atomic fact keys, reference rubric, answerability, category/difficulty, citation requirements, abstention policy, task type and review provenance. Dataset and corpus versions/checksums are frozen with each run. Content checksums use SHA-256 over sorted-key, compact, UTF-8 JSON; prompt/tool/pricing source files also have hashes. Labels were authored before measuring the actual ranking, not inferred from the retriever's results. Generator extraction rules live in the application and never import this dataset or evaluator fact catalog. The runner sends no labels/expected answers to `/ask`.

## Honest review status

The initial labels were checked against quoted synthetic source evidence by the implementation author. They are `author_reviewed`, **not independently human-reviewed or calibrated**. Independent human review and any LLM-judge validation remain pending. Do not describe these scores as validated live-model accuracy. The deliberately small closed-domain rubric makes engineering checks reproducible; it does not establish broad semantic evaluation quality.

Manual review workflow:

1. Read the declared corpus first. For each question, identify all necessary source documents without looking at the measured ranking or generated output. Separate missing knowledge from ambiguous requests and tool-dependent tasks.
2. Check every expected atomic value, approved alternative and evidence quote. Verify answerability, relevance, citation obligations and what adequate abstention would say. Record uncertain labels as uncertain/unreviewed instead of silently calling them human-reviewed.
3. Keep a separate review artifact with reviewer identity, date, dataset checksum, case ID, proposed corrections, rationale and source evidence. Obtain independent human annotations before claiming human review or calibration. No human annotations were collected in this checkpoint.
4. Reconcile disagreements explicitly. Never rewrite stored versions/results. A changed dataset requires a new version and checksum; the persistence boundary rejects reusing an existing dataset version with different content. Validate via `evaluation.dataset.load(path)` before using a new dataset; this initial runner intentionally defaults to v1. Review any new corpus version and regenerate independent labels accordingly.
5. Preserve human judgments separately from constrained scores. Current automated runs label independent review pending; there is no automatic human-judgment import, judge service, cross-run promotion or deployment gate.

Human/free-form review rubric: break the **actual displayed answer** into atomic claims; mark each claim supported, contradicted, unsupported or uncertain using actually supplied evidence. Separately judge correctness against authoritative source truth and expected facts; mark missing required facts. Check each cited ID for existence, supplied availability and support for that claim; mark citation-required claims lacking supported citations. Judge whether abstention was appropriate. Preserve evidence IDs/quotes and rationale, reviewer identity and rubric version. Uncertain cases remain pending; do not coerce them into zero or perfect scores. An optional future judge would need its own identity/prompt version, validated structured judgments and independent human agreement analysis. None is claimed here.

## Diagnostic fixture provenance

The baseline is actual deterministic application execution. Controlled faulty-output experiments explicitly transform its returned claim objects, re-render the displayed answer and preserve both original and evaluated outputs in PostgreSQL. These verify the evaluator, not the assertion that the agent naturally produced those errors. Wrong fact, unsupported extra claim, missing fact, wrong/fabricated/missing citation and inappropriate abstention have distinct expected diagnostics. The trace still describes the original application execution; the result prominently identifies the diagnostic transform.

The unavailable-trace diagnostic uses the real returned trace identity but sends its lookup to a deliberately unavailable loopback endpoint. It records pending visibility; it does not fabricate a nonexistent trace ID or assert export failure. The normal Collector may persist that trace independently. An initial run during Docker restoration also retained genuine pending visibility when exports were unavailable. Persisted trace visibility is a snapshot, not a live join/foreign key.
