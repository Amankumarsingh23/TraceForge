# Local burn policy and incident lifecycle

Rules combine long-window AND short-window burn >= threshold at one whole-second UTC cutoff. Overall and both windows must satisfy their evidence policies; otherwise the rule is UNKNOWN. A valid non-breach is HEALTHY for this rule, even if the objective is still violated: resolving an alert means its burn condition ended, not that the entire historical budget was restored.

The measured demo uses target0.9, objective/long20s, short10s, threshold2, count>=3, supported coverage>=0.6 per declared writer, critical severity, confirm1/recover1. These intentionally short learning settings are not production recommendations. A production-shaped example is a99.9%30-day objective with1h/5m14.4x and6h/30m6x rules; the current raw adapter cannot evaluate the full30-day/6-hour scope and therefore returns UNKNOWN. The [Google SRE workbook](https://sre.google/workbook/alerting-on-slos/) explains the multiwindow approach; thresholds require workload-specific calibration.

The scheduler accepts at most8 explicit keys via `TRACEFORGE_SLO_ACTIVE`, one sequential worker, cadence `TRACEFORGE_SLO_CADENCE` (default10s; valid1s–5m), a3s ingestion delay and20s deadline per objective. It is disabled with no active keys. Cutoffs align to the cadence; no unbounded worker spawning or historical catch-up loop. Cancellation drains before database closure. Scheduling can be slow under bounded query timeouts; this is a local evaluator, not a high-availability notification system.

INACTIVE -> PENDING -> FIRING requires the configured consecutive valid breaches (1–10). Consecutive valid non-breaches resolve after recover1–10. UNKNOWN preserves active state, records evidence status and resets streaks; it never means recovery. Only strictly newer cutoffs advance state. Stale evaluations and same-cutoff revisions remain immutable history with no lifecycle effects.

A PostgreSQL transaction locks the definition row before creating/updating rule heads, then locks the head and atomically stores evaluation, incident and events. Stable definition/rule fingerprints, a unique active-incident constraint, deterministic event identities and evaluation uniqueness prevent duplicate firing under retries/concurrency. A resolved episode remains immutable history; a later breach creates a new incident. FIRING and RESOLVED events each retain a contributing evaluation link. Row-lock behavior follows [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html), checked against current documentation on2026-11-14. The local PostgreSQL image/version remains unchanged.

Definitions/evaluations/events reject SQL UPDATE/DELETE through triggers. Alert heads and incident summary state are mutable transactionally. This is application audit history, not administrator-proof tamper evidence. There is no notification delivery, escalation, silence/ack API, remediation or external paging. Reads are GET-only, parameterized, deadline/concurrency/row/byte bounded and cursor paginated; they do not introduce authentication or tenant isolation. Keep Compose and Next bound to loopback. Namespace filters are scope selection, not authorization.
